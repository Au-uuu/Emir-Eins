# WD14 打标：结果进日志（可观测）+ 按图片内容缓存（省 ~2 秒）

日期：2026-10-08

## 背景

用户要求「检查一下这个匹配图片的功能」。把「图片进来 → 识别 → 喂给模型」这条链路
整个盘了一遍，并量了线上真实耗时：

| 时刻 | 事件 | 间隔 |
|---|---|---|
| 19:30:35 | 收到消息 | |
| 19:30:39 | **WD14 首次加载**（467MB 模型） | |
| 19:30:47 | 回复（图片描述） | **12 秒** |
| 19:31:03 | 收到 | |
| 19:31:07 | 回复（同一条描述） | **4 秒** |

即：每张图 ≈ 打标 2 秒 + 视觉调用 2 秒；重启后首张 12 秒（含模型加载）。
ONNX 会话常驻约 900MB（实测 bot 进程 RSS 917MB），服务器 3.7G 内存无压力。

查出两个问题：

1. **功能不可观测**：日志里既没有打标结果，也没有「命中/未命中」。机器人只描述、
   不报角色名时，**无法判断是「WD14 没命中」还是「命中了但模型没用」**——
   排查时只能靠猜。这正是本次「检查功能」卡住的地方。
2. **重复图白跑推理**：实测同一张图 20 秒内被重发，2 秒推理又完整跑一遍。

## 改动

`tagger.py`：

- **结果缓存**：`tag_image()` 按**图片内容 sha256** 缓存 `(角色, 作品)` 标签，
  LRU 上限 128 条。命中直接返回 → 第二次起 ≈ 0 秒。只缓存**真的跑过推理**的结果
  （模型缺失时结果恒为空对，缓存没有意义）。
- **打标结果进日志**：新增 `_fmt_tags()`，每次推理后记一行
  `[打标] 角色=hatsune_miku；作品=vocaloid` 或 `[打标] 无标签命中（阈值 0.35）`；
  缓存命中记 `[打标] 缓存命中：…`。之后「认不出角色」到底是哪一环的问题，看日志即可。

`_test_tagger.py`（新增，16 项断言）：模型缺失时静默降级、同一张图只推理一次、
不同内容重新推理、LRU 淘汰最旧、推理抛异常时返回空对且不写缓存、日志格式。
**不依赖 onnxruntime / 模型文件**（推理层整个替换成假的），所以本机就能跑。

## 附带修掉一个测试污染

`_test_persona.py` 硬断言「视觉模型默认 qwen3-vl-flash」，而**服务器 `.env` 配的是
`qwen3-vl-plus`** → 本地过、服务器挂一项。与之前 `_test_ark_news.py` 关键词那次同类：
**测试不该依赖运行环境**。已改成断言前先把环境变量清掉，本地（有/无该变量）与
服务器均确定。

## 备注

- 缓存只解决**重复图**；首次出现的图仍需 ~2 秒 CPU 推理（视觉调用另算）。
- 若日后觉得这 2 秒不值，可以按 `QQ_BOT_TAGGER_*` 加开关，或只对「模型可能不认识
  的新游戏图」打标——目前无差别打标，实现最简单。
