# /help 改为发送图片；移除失效的帮助按钮

日期：2026-10-02

## 需求

1. `/help` 这类长文本在 QQ 里一发出来就占满整屏，希望**转成图片显示得更紧凑**。
2. 背景用指定的插画（`C:\DSH\image\118728153_p0.jpg`）。
3. 第一版发出去后体积偏大、上传慢，要求压缩。
4. 用户确认**从未见过帮助按钮**，要求把按钮删掉。

## 方案

| 模块 | 职责 |
|---|---|
| `help_image.py` | 渲染帮助图 + 内存缓存（帮助文本静态，只渲染一次） |
| `text_image.py` | 通用文本转图片；本次新增 `background` / `panel_alpha` / `image_top` / `panel_blur` / `columns` |
| `bot.py` | `send_help()` 优先发图，图片走不通（无背景图 / 渲染失败 / 上传失败）退回文本 |

**「显示更小」的原理**：QQ 把图片按聊天窗口宽度等比缩放，所以

```
屏上字号 ≈ font_size × (聊天窗口宽度 / 画布宽度)
```

1280 宽 + 28px 字号 → 手机（约 400pt）上约 8.8pt，比 QQ 默认文本（16~17pt）小一半。

### 为什么输出 JPEG 且用 4:4:4

带照片背景时 PNG 压不动（1280×1783 的图约 **2.2MB**）。转 JPEG 后降到几百 KB。
色度采样强制 4:4:4：与 `q76 + 4:2:0` 体积相当，但**能保住中文小字的边缘**——
4:2:0 会先牺牲色度细节，照片上的小字会发毛。

### 实测尺寸与耗时（服务器真实数据）

服务器真实上行约 **170 KB/s**（标称 3Mbps 峰值的 45%），耗时按此估算：

| 场景 | q85（初版） | q72（现行） |
|---|---|---|
| 群 / 普通人（18 行） | 381 KB · 2.2s | **254 KB · 1.5s** |
| 私聊管理员（25 行） | 498 KB · 2.9s | **331 KB · 1.9s** |

首次渲染 1.8 秒，之后命中缓存（0.0000 秒）。

## 试过但否掉的方案

- **两栏排版**：本以为能在宽度不变的前提下把高度砍半，**实测反而更高**
  （普通人 1216→1599，管理员 1783→1896）。原因：每栏只有 590px 宽，那些本来
  刚好一行的长指令被迫折成两行，总行数增加。宽度本来就被用满了。
  `columns` 参数保留但**默认单栏**。
- **磨砂玻璃面板**（`panel_blur`）：用户明确不要。参数保留备用。
- `q76 + 4:2:0`：体积与 `q72 + 4:4:4` 相当，但文字边缘更差。

## 一个反直觉的实测结论

**面板越透明，文件越大**：背景细节透出来 = 图像熵更高 = 更难压缩。
所以用户选的 `panel_alpha=120` 本身就比不透明的版本贵一些；
要更小可以先动这个旋钮（120→160 约再省 15%）。

## 按钮：发现与移除

### 原设计

`bot.py` 里有四个部分：`HELP_BUTTONS` 常量、`build_help_keyboard()`、
`on_interaction_create()`（点击回调）、`_handle_help_button()`（实际动作），
`/help` 的文本消息会挂上三个按钮（功能与指令 / 随机来张图 / 图库列表）。

### 日志证据：按钮一直是死的

`journalctl` 里 9/21~9/23 共有 **7 次按钮点击事件**：

```
9月 21 10:53:29  [按钮] data= group=5C04C69877
9月 22 18:44:19  [按钮] data= group=2D371B6629
9月 23 13:42:20  [按钮] data= group=7AF61E9EA3
```

注意每一行的 `data=` **都是空的**，而处理器里：

```python
if not button_data:
    return          # ← 空 data 直接丢弃，什么都不做
```

也就是说：**按钮能显示、能点击，但点击后机器人这边永远无事发生**。
（推测 botpy 1.2.1 里 `button_data` 不在 `interaction.data.resolved` 这个路径上。）
另外 `_handle_help_button` 用的是 `post_group_message` 且不带 `msg_id`，
属于**主动消息**，未认证的机器人本来就发不出去——即使 data 修好了也还要改。

### 结论与处置

用户确认**从未见过按钮**（改成图片后就彻底没有了），且暂时不需要 → 全部移除。

移除清单：

| 位置 | 内容 |
|---|---|
| `bot.py` | `HELP_BUTTONS` 常量、`build_help_keyboard()`、`on_interaction_create()`、`_handle_help_button()`、`_reply_image_bytes` 的 `keyboard` 参数、`_image_keyboard_ok` 试探逻辑 |
| `bot.py` `main()` | intents 里的 `interaction=True`（不再订阅 INTERACTION_CREATE） |
| 测试 | `_test_commands.py` 改断言「不再带 keyboard」；`_test_help_image.py` 降级路线简化为「图片 → 文本」 |

> 想找回按钮：`git log` 里找本次提交之前的那一版 `bot.py`。
> ⚠️ 恢复时**别忘了 intents 里的 `interaction=True`**，否则点击事件根本不会推送。

## 备注：一个我犯过的错

改图片后我曾断言「**按钮没丢**」，依据只是「接口没报错」。这是**无效推断**——
API 接受带 keyboard 的富媒体消息，不等于客户端会渲染按钮。用户当场质疑
「哪来的按钮」，回去翻日志才发现按钮不但没显示，**而且从来就没生效过**。
教训：涉及「客户端到底显示了什么」的问题，只有用户的眼睛或客户端日志能作证，
接口返回 200 不能。
